### [심각도: 중] VAD 모델 초기화 실패 시 리소스 미정리

- **파일**: data/voice/VoiceRecordingManager.kt:105-112
- **증상**: 
  VoiceRecordingManager.start()의 catch 블록에서 exception 발생(특히 vadProcessor.initialize() 실패) 시, 
  vadProcessor.close()를 호출하지 않아 VAD 모델 리소스(Silero VAD 라이브러리의 할당된 메모리)가 해제되지 않는다.
  반복적인 start() 실패 시나리오(권한 부족, 마이크 이상, VAD 모델 로드 실패 등)에서 메모리 누수 누적.

- **근거**:
  ```kotlin
  } catch (e: VadException) {
      _vadState.value = VadState.Error(e)
      listener?.onError(e)
      // ← vadProcessor.close() 호출 없음
  } catch (e: Exception) {
      val vadException = VadException.UnknownError(cause = e)
      _vadState.value = VadState.Error(vadException)
      listener?.onError(vadException)
      // ← vadProcessor.close() 호출 없음
  }
  ```
  
  같은 메서드의 정상 종료 경로에서는 stop()을 호출하고, 
  stop() 내부에서 vadProcessor.close()를 호출(라인 123)하지만,
  catch 블록은 이 경로를 거치지 않고 직접 종료된다.


### [심각도: 중] [요검증] 녹음 중지 시 stopRecording() 중복 호출로 인한 Race Condition

- **파일**: 
  - data/voice/VoiceRecordingManager.kt:120-135 (stop 메서드)
  - data/voice/AudioRecorder.kt:76-98 (Flow collection), 105-117 (stopRecording 메서드)

- **증상**: 
  VoiceRecordingManager.stop()이 호출될 때, recordingJob?.cancel()은 비동기로 진행되지만
  즉시 다음 라인의 audioRecorder.stopRecording()이 실행된다.
  동시에 Flow의 try-finally 블록에서도 stopRecording()이 호출되어,
  두 스레드에서 거의 동시에 audioRecord?.stop()과 audioRecord?.release()를 호출할 수 있다.
  
  AudioRecord 클래스는 멀티스레드 안전성을 보장하지 않으므로,
  이는 IllegalStateException, NullPointerException, 또는 리소스 중복 해제를 야기할 수 있다.
  
  구체적 시나리오:
  1. start() 호출 → audioRecorder.startRecording() Flow collection 시작
  2. stop() 호출 → recordingJob?.cancel() 신호 전송 (비동기, blocking 안 함)
  3. audioRecorder.stopRecording() 즉시 실행 (Thread A)
  4. 동시에 Flow의 finally 블록이 stopRecording() 실행 (Thread B)
  5. Thread A: audioRecord?.stop() 실행
  6. Thread B: audioRecord?.recordingState 확인 중
  7. Thread A: audioRecord?.release() 실행
  8. Thread B: audioRecord?.stop() 호출 (이미 released된 객체)

- **근거**:
  ```kotlin
  // VoiceRecordingManager.stop() - 라인 119-135
  fun stop() {
      recordingJob?.cancel()  // async: cancel signal만 전송, blocking 아님
      recordingJob = null
      audioRecorder.stopRecording()  // sync: 즉시 실행
      vadProcessor.close()
      ...
      scope?.cancel()
      scope = null
  }
  
  // AudioRecorder.startRecording() - 라인 76-98
  fun startRecording(): Flow<ShortArray> = flow {
      ...
      audioRecord?.startRecording()
      ...
      try {
          while (coroutineContext.isActive) { ... }
      } finally {
          stopRecording()  // cancel 신호 후에도 실행될 수 있음
      }
  }
  
  // AudioRecorder.stopRecording() - 라인 105-117
  fun stopRecording() {
      audioRecord?.let {
          try {
              if (it.recordingState == AudioRecord.RECORDSTATE_RECORDING) {
                  it.stop()  // Thread-unsafe
              }
              it.release()  // Thread-unsafe
          } catch (e: Exception) { }
      }
      audioRecord = null
  }
  ```
  
  recordingJob?.cancel()은 Job 취소 신호만 보내고,
  코루틴이 정말로 종료될 때까지 대기하지 않는다.
  따라서 이후의 audioRecorder.stopRecording() 호출과
  Flow의 finally 블록의 stopRecording() 호출이 race condition을 형성한다.


### [심각도: 중] Error/Completed 상태에서 stop() 없이 start() 재호출 시 이전 scope 미정리

- **파일**: data/voice/AudioRecordManager.kt:79-103
- **증상**:
  AudioRecordManager의 상태가 Error 또는 Completed일 때,
  stop()을 명시적으로 호출하지 않고 start()를 다시 호출하면,
  기존 scope에 대한 참조가 손실되어 리소스 누수가 발생한다.
  
  구체적 시나리오:
  1. start() 호출 → scope1 생성, state = Preparing
  2. 예외 또는 정상 완료 → state = Error 또는 Completed
  3. 사용자가 stop() 호출 없이 바로 start() 호출
  4. state 확인: Error/Completed는 Preparing/Listening/Recording 조건에 없으므로 통과
  5. scope2 = new CoroutineScope(...) → scope1 참조 손실
  6. scope1의 job이 여전히 active하면 미정리, 또는 이미 complete되었어도 scope 객체는 GC 대기

- **근거**:
  ```kotlin
  fun start() {
      Log.d(TAG, "start() called, current state: ${_state.value}")

      if (_state.value is AudioRecordState.Preparing ||
          _state.value is AudioRecordState.Listening ||
          _state.value is AudioRecordState.Recording
      ) {
          return
      }

      scope = CoroutineScope(SupervisorJob() + Dispatchers.Main)  // 이전 scope 참조 덮어씀
      
      _state.value = AudioRecordState.Preparing
      ...
  }
  ```
  
  stop() 메서드에서는 정상적으로 scope?.cancel() 호출(라인 116)하지만,
  Error/Completed 상태에서 start()를 다시 호출할 경우
  scope 참조가 직접 덮어씌워져 이전 scope의 cancel() 기회 없이 버려진다.

### 발견 #1 — 기각하되 정정된 형태로 유효

보고된 시나리오("initialize() 실패 시 close 미호출로 누수")는 사실과 다르다.
VadProcessor.initialize()(VadProcessor.kt:33-46)에서 `build()`가 예외를 던지면
`vad` 필드는 null인 채로 남으므로, close()를 호출해도 해제할 것이 없다.
초기화 **실패** 경로에는 누수가 없다.

다만 인접한 실제 누수 경로가 있다:

#### [심각도: 중] 에러 후 stop() 없이 재시작하면 이전 VadSilero 인스턴스가 close 없이 덮어써짐

- 파일: data/voice/VadProcessor.kt:35, data/voice/VoiceRecordingManager.kt:80
- 증상: 초기화가 **성공**한 뒤 녹음 중 에러(RecordingError 등)로 recordingJob이
  종료되면 vadProcessor는 열린 채 남는다. 이 상태에서 stop() 없이 start()가
  다시 불리면 — AudioRecordManager.start()의 가드는 Error 상태를 통과시키고,
  VoiceRecordingManager.start()의 가드(`recordingJob?.isActive`)도 종료된 job이라
  통과 — initialize()가 기존 `vad`를 close하지 않고 새 인스턴스로 덮어써
  Silero VAD의 네이티브(ONNX) 리소스가 누수된다. 에러→재시도가 반복될수록 누적.
- 근거: VadProcessor.kt:35의 `vad = Vad.builder()...build()`는 기존 인스턴스를
  확인하지 않는다. ConversationViewModel의 recoverRecordingAfterError()는
  resumeListening()(stop 후 start)을 쓰므로 안전하지만,
  startRecording()(ConversationViewModel.kt:810)은 audioRecordManager.start()를
  직접 호출하므로 Error 상태에서 이 경로가 열려 있다.

### 발견 #2 — 부분 확증 (경합은 실재, 실질 영향은 제한적)

`audioRecord` 변수에 대한 비동기화 이중 stopRecording() 경합(Main 스레드의
stop() vs IO 스레드 flow의 finally)은 코드상 실재한다. 다만 stopRecording()
전체가 try/catch로 감싸져 있어(AudioRecorder.kt:107-114) 이중 해제 시 예외는
무시되고, 실질 피해는 제한적이다. [요검증] 유지가 적절하다.

**더 중요한 인접 버그**: VoiceRecordingManager.kt:108의 `catch (e: Exception)`이
**CancellationException을 삼킨다.** stop()이 recordingJob을 취소하면 collect
지점에서 CancellationException이 던져지고, 이것이 catch(Exception)에 잡혀
VadState.Error 전이 + listener.onError() 발화로 변환된다 — 즉 정상적인 stop()이
에러 콜백을 유발한다. 이 동작은 이미 알려져 있어 ConversationViewModel.kt:177-179에
주석과 `wasAudioStoppedForBackground` 플래그로 우회 중이지만, 우회는 백그라운드
전환 경로만 커버하고 나머지 stop 경로는 상태 가드에 의존한다. 근본 원인
(CancellationException을 rethrow하지 않는 것)을 고치면 하위의 방어 코드가
불필요해진다. Kotlin 코루틴 표준 사례상 catch(Exception)에서
CancellationException은 반드시 재던져야 한다.

### 발견 #3 — 확증 (CONFIRMED)

AudioRecordManager.start()(79-103행)의 가드가 Preparing/Listening/Recording만
확인하므로 Completed/Error/**Processing** 상태에서 start()가 통과하고, 90행에서
이전 scope를 cancel 없이 덮어쓴다. 이전 scope의 observeVadState() collector는
StateFlow 수집이라 스스로 끝나지 않으므로 영구 누수이며, collector가 중복되면
onReady() 중복 호출도 가능하다. 가드에 없는 Processing 상태도 동일 경로로
통과한다는 점은 haiku 보고에 빠져 있어 보충한다. 발생 경로는
ConversationViewModel.startRecording()의 직접 start() 호출(810행)이다.
