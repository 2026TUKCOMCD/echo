# T11. 서버 — 대화/AI/음성 파이프라인 버그 감사 결과

## 발견 목록

### [심각도: 상] OpenAI API 타임아웃 설정 부재
- **파일**: `voice/config/OpenAIFeignConfig.java`
- **증상**: OpenAIClient는 Feign 기본 타임아웃인 1초로 설정되어, OpenAI API 응답이 1초를 초과하면 즉시 `SocketTimeoutException`이 발생합니다. 실제 사용 환경에서 대화 시작(generateGreeting)이나 응답 생성(generateResponse)이 1초 이내에 완료되기 어려우므로, 빈번한 타임아웃 에러가 발생할 수 있습니다.
- **근거**: 
  - OpenAIFeignConfig.java 1-26줄에는 `RequestInterceptor`만 있고 타임아웃 설정이 없습니다.
  - 반면 AzureTtsFeignConfig.java 26-28줄과 SupertoneFeignConfig.java 20-22줄에는 `feign.Request.Options(10_000, 30_000)`로 명시적 타임아웃이 있습니다.
  - Feign 기본값: connect 1000ms, read 1000ms (Feign 문서 참고)

### [심각도: 상] 대화 히스토리의 동시성 안전성 결함
- **파일**: `context/service/ContextService.java:134-144` 및 `context/domain/UserContext.java:26`
- **증상**: 같은 사용자로부터 동시에 여러 요청이 들어오는 경우 (예: `/api/conversations/message`와 `/api/conversations/tts-retry`를 동시에 호출), `conversationHistory` ArrayList에 대한 비동시적 접근으로 인해 데이터 손상이 발생합니다. 예를 들어 Thread A가 읽는 도중 Thread B가 add()를 호출하면, 일부 턴이 손실되거나 히스토리 순서가 뒤바뀔 수 있습니다.
- **근거**:
  - ContextService 29줄: `private final ConcurrentHashMap<Long, UserContext> contextStore`는 thread-safe하지만,
  - UserContext 26줄: `private List<ConversationTurn> conversationHistory = new ArrayList<>()`는 thread-unsafe한 ArrayList입니다.
  - addConversationTurn 143줄: `context.getConversationHistory().add(turn)`에서 ArrayList의 add() 호출이 동기화되지 않습니다.
  - AIService 77줄: `List<ConversationTurn> history = context.getConversationHistory()`에서 반환된 리스트는 원본 참조이므로, 다른 스레드의 수정이 영향을 줍니다.

### [심각도: 중] 외부 API 호출이 DB 트랜잭션 내에서 실행
- **파일**: `conversation/service/ConversationService.java:37-65` (startConversation) 및 `conversation/service/ConversationService.java:68-92` (processUserMessage)
- **증상**: 두 메서드가 `@Transactional`로 표시되어 있으면서, 내부에서 OpenAI API(aiService.generateGreeting, aiService.generateResponse)와 TTS API(voiceService.textToSpeech)를 호출합니다. 외부 API의 응답 시간(보통 수 초)이 길면, 해당 시간 동안 DB 트랜잭션과 커넥션이 점유됩니다. 많은 사용자의 동시 요청 시 DB 커넥션 풀이 빠르게 고갈되어, 다른 요청들이 커넥션을 얻지 못해 응답 시간이 급증하거나 `HikariPool - Connection is not available` 에러가 발생합니다.
- **근거**:
  - ConversationService 37줄: `@Transactional public ConversationStartResponse startConversation(...)`
  - 같은 메서드의 52줄: `String firstMessage = aiService.generateGreeting(...)` (OpenAI API 호출)
  - 같은 메서드의 55줄: `byte[] audioData = voiceService.textToSpeech(...)` (Azure TTS 또는 Supertone 호출)
  - 68줄의 `processUserMessage`도 동일한 구조
  - 트랜잭션이 이들 API 호출의 완료까지 유지되므로, 느린 API 응답이 직접 DB 커넥션 점유 시간으로 이어집니다.

### [심각도: 중] [요검증] 다중 API 클라이언트의 타임아웃/재시도 설정 불일치
- **파일**: `voice/config/AzureTtsFeignConfig.java`, `voice/config/SupertoneFeignConfig.java`, `ai/client/OpenAIClient.java`
- **증상**: 외부 API별 타임아웃 설정이 서로 다릅니다. Azure TTS와 Supertone은 각각 10초 연결 + 30초 읽기이지만, OpenAI는 설정이 없어 기본 1초입니다. 또한 Feign 레벨의 재시도 정책이 없어, 일시적 네트워크 오류나 서버 지연에 취약합니다. OpenAI API 타임아웃 발생 시 사용자에게 500 에러가 그대로 전파됩니다 (AIService.java 89-92줄).
- **근거**:
  - OpenAIFeignConfig 1-26줄: 타임아웃 설정 없음 (Feign 기본값 1초 적용)
  - AzureTtsFeignConfig 26-28줄: `new feign.Request.Options(10_000, 30_000)`
  - SupertoneFeignConfig 20-22줄: `new feign.Request.Options(10_000, 30_000)`
  - AIService 89-92줄: FeignException을 즉시 AIException으로 변환하여 재시도 없음
  - [요검증] 실제 프로덕션 환경에서 OpenAI API의 평균 응답 시간을 측정하여 확인 필요

### [심각도: 하] 프롬프트 인젝션 위험 (제한적 영향)
- **파일**: `prompt/service/PromptService.java:85-95` (사용자 선호도) 및 `ai/service/AIService.java:140-143` (STT 결과)
- **증상**: UserPreferences의 필드들(name, hobbies, familyInfo, preferredTopics)과 STT 결과(userMessage)가 검증 없이 프롬프트에 직접 삽입됩니다. 악의적 사용자가 데이터베이스에 특수 문자나 프롬프트 지시를 저장하거나, 음성 입력을 조작하면, AI의 응답을 의도하지 않은 방향으로 유도할 수 있습니다. 예: name을 "'; IGNORE SYSTEM INSTRUCTION; //"로 설정.
- **근거**:
  - PromptService 85줄: `variables.put("userName", preferences.getName())`
  - PromptService 91-94줄: hobbies, job, family, preferredTopics가 검증 없이 삽입
  - AIService 140-143줄: STT 결과인 userMessage가 그대로 messages 배열에 추가
  - 다만, OpenAI API의 역할 기반 메시지 구조(role: "user", "assistant", "system")가 어느 정도 격리를 제공하므로 완전한 프롬프트 오버라이드는 어려울 수 있음 [요검증]

## 체크리스트 판정

### 1. AI 클라이언트(OpenAI) 호출의 타임아웃/재시도 설정
**상태**: 발견 #1, #4  
**판정**: OpenAIFeignConfig에 타임아웃 설정이 없어 기본값 1초가 적용되며, 재시도 정책도 없습니다. 외부 API 오류가 500으로 직접 노출됩니다.

### 2. 대화 세션 저장소 동시성 안전성
**상태**: 발견 #2  
**판정**: ConcurrentHashMap은 thread-safe하지만, 내부의 ArrayList conversationHistory가 thread-unsafe합니다. 동시 요청 시 데이터 손상 위험이 있습니다.

### 3. 업로드된 음성 파일의 크기/형식 검증
**상태**: 문제 없음  
**판정**: VoiceServiceImpl에서 validateAudioFile()로 크기(25MB) 및 형식(mp3, wav 등) 검증이 구현되어 있습니다. 임시 파일 정리는 Spring이 자동으로 관리합니다.

### 4. 프롬프트 조립 시 프롬프트 인젝션
**상태**: 발견 #5  
**판정**: 사용자 입력 데이터가 검증 없이 삽입되지만, OpenAI의 역할 기반 메시지 구조로 인해 완전한 공격은 제한적입니다 [요검증].

### 5. 트랜잭션 경계 안에서 외부 API 호출
**상태**: 발견 #3  
**판정**: ConversationService의 startConversation과 processUserMessage가 @Transactional 내에서 OpenAI/TTS API를 호출하여, DB 커넥션 풀 고갈 위험이 있습니다.

## 검증 노트 (검증자: Fable 5, 2026-07-07)

위 보고는 haiku가 작성한 원본이며, 아래는 코드·설정 재확인을 통한 교차 검증
결과다. **핵심 정정**: haiku가 심각도 "상"으로 올린 두 건 모두 사실 오류 또는
과대평가이며, 실제 가장 심각한 문제는 haiku가 "중"에 둔 트랜잭션 발견이다.

### 발견 #1 — 기각(사실 오류), 단 다른 형태의 실제 문제로 대체

**"Feign 기본 타임아웃 1초"는 틀렸다.** Feign의 `Request.Options` 기본값은
connect 10초 / **read 60초**이며(Spring Cloud OpenFeign도 동일), OpenAIFeignConfig
(OpenAIFeignConfig.java 전체)에는 타임아웃 지정이 없으므로 이 기본값이 적용된다.
따라서 "1초 초과 시 빈번한 타임아웃"이라는 증상은 발생하지 않는다 — 방향이
정반대다.

실제 문제는 **read 타임아웃이 너무 길다(60초)**는 것이다. Azure/Supertone은
`Request.Options(10_000, 30_000)`로 30초를 명시(AzureTtsFeignConfig.java:27,
SupertoneFeignConfig.java:21)한 반면, OpenAI/STT(Whisper)는 무설정이라 최대 60초까지
스레드·(그리고 발견 #3과 결합해) DB 커넥션을 붙잡는다. haiku가 제안한 "1초라서
문제 → 20~30초로 늘려라"는 잘못된 처방이고, 올바른 방향은 명시적 타임아웃을
**설정해 상한을 낮추는 것**이다. 심각도 중.

### 발견 #2 — 확증하되 심각도 하향 (상→중, 트리거 요검증)

`conversationHistory`가 평범한 ArrayList이고 add()가 비동기화라는 지적은 코드상
맞다(UserContext.java:26, ContextService.java:143). 다만 데이터 손상이 실제로
일어나려면 **같은 userId의 요청이 시간적으로 겹쳐야** 하는데, 이 앱은 어르신
1인당 턴 단위(발화→응답)로 진행되는 음성 대화라 동일 사용자 동시 요청이
정상 흐름에서 드물다. haiku가 든 "message와 tts-retry 동시 호출" 예도, tts-retry는
리스트를 읽기만 하고 add하지 않으므로(ConversationService.java:97,102) 손상보다는
드문 순간의 `ConcurrentModificationException` 정도다. 실제 피해 가능성이 낮아
"상"은 과하다 → 중, 트리거 현실성은 [요검증].

### 발견 #3 — 확증, 그리고 이번 태스크의 실질 최고 심각도

`processUserMessage`(ConversationService.java:67)와
`startConversation`(37), `endConversation`(110)이 `@Transactional`인데 그 안에서
STT→OpenAI→TTS 외부 호출이 순차 실행된다(73,78,81행). 여기에 결정적 정황을
보강한다: **processUserMessage는 DB를 직접 건드리지 않는다.** 컨텍스트는 인메모리
ConcurrentHashMap(ContextService)에서 읽고, 히스토리도 인메모리 리스트에 add할
뿐이다. 즉 이 트랜잭션은 **실질 DB 작업이 없는데도** HikariCP 커넥션 하나를
열어 세 번의 느린 외부 호출(발견 #1대로 각 최대 60초) 동안 붙잡는다. 동시
사용자가 풀 크기를 넘으면 `Connection is not available`로 전체 대화 API가 마비된다.
발견 #1의 과도한 타임아웃과 곱해져 위험이 증폭된다. 심각도 중이나 부하 시 상에
근접 — 우선 조치 1순위로 올린다. 처방은 세 메서드에서 @Transactional 제거 또는
외부 호출을 트랜잭션 밖으로 분리.

### 발견 #4 — 발견 #1의 중복, 통합 처리

#1과 같은 사실 오류("기본 1초")를 공유한다. 유효한 알맹이는 "OpenAI/STT에만
명시적 타임아웃·재시도가 없다"는 점 하나로, #1에 흡수한다. 별건으로 세지 않음.

### 발견 #5 — 유지 (하)

STT 결과·사용자 선호도가 검증 없이 프롬프트에 삽입되는 것은 맞고, role 기반
구조 덕에 영향이 제한적이라는 판단도 타당하다. 심각도 하, [요검증] 유지.
(예시로 든 `IGNORE SYSTEM INSTRUCTION`류는 system role 프롬프트를 실제로
덮어쓰지는 못하므로 과장에 주의.)

### 체크리스트 판정 정정
