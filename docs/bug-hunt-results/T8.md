# T8. 권한 처리 흐름 코드 감사

## 발견 목록

### [심각도: 중] [요검증] Activity의 onResume 후 권한 상태가 명시적으로 재확인되지 않음
- **파일**: `presentation/permission/UnifiedPermissionHandler.kt:56-286`
- **증상**: 사용자가 설정 앱에서 권한을 변경(허용/거부)한 후 앱으로 돌아올 때, 권한 상태가 자동으로 업데이트되지 않을 수 있습니다. 특히 온보딩이 완료된 상태(`hasCompletedOnboarding = true`)에서는 권한 다이얼로그가 다시 표시되지 않을 수 있습니다.
  - 구체적 시나리오:
    1. 사용자가 온보딩 완료 (권한 플로우 끝남)
    2. 나중에 설정 앱에서 마이크 권한 거부 (또는 위치 권한 변경)
    3. 앱으로 돌아옴
    4. 마이크 권한이 거부되었지만, MicrophonePermissionSettingsDialog가 표시되지 않을 수 있음

- **근거**: 
  - UnifiedPermissionHandler는 Composable이며, Activity의 생명주기(onResume)와 명시적으로 연결되지 않음 (라인 56-60)
  - LaunchedEffect가 권한 단계 변화에만 반응하고, Activity 재개 이벤트에는 반응하지 않음 (라인 141-208)
  - Composable의 자동 재구성에만 의존하며, 이는 보장되지 않음
  - 라인 211-220에서 온보딩 완료 후에는 명시적 권한 확인이 제한적임

**참고**: 현재 구현에서 Composable이 재구성되면 권한이 재확인될 수 있지만, 명시적인 생명주기 훅 없이는 완전히 신뢰할 수 없습니다.

### [심각도: 중] 포그라운드 위치 권한 거부 후에도 사용자에게 거부 상태 알림이 부족함
- **파일**: `presentation/permission/UnifiedPermissionHandler.kt:94-106`
- **증상**: 사용자가 포그라운드 위치 권한(ACCESS_FINE_LOCATION)을 거부하면, 앱이 조용히 NOTIFICATION 단계로 진행합니다. 사용자는 위치 권한이 거부되었다는 것을 알 수 없고, 위치 기능이 작동하지 않는 이유를 파악할 수 없습니다.
  - 구체적 시나리오:
    1. 온보딩 중 포그라운드 위치 권한 거부
    2. 앱에서 거부 상태를 나타내는 다이얼로그나 메시지 없음
    3. 나중에 사용자가 위치 기반 기능을 시도해도 작동하지 않음

- **근거**:
  ```kotlin
  // 라인 94-106: 포그라운드 위치 권한 요청 결과 처리
  val foregroundLocationLauncher = rememberLauncherForActivityResult(
      ActivityResultContracts.RequestMultiplePermissions()
  ) { permissions ->
      val granted = permissions[Manifest.permission.ACCESS_FINE_LOCATION] == true ||
              permissions[Manifest.permission.ACCESS_COARSE_LOCATION] == true
      if (granted) {
          currentStep = PermissionStep.LOCATION_BACKGROUND
      } else {
          // 위치는 선택이므로 다음으로 진행  ← 사용자 피드백 없음
          currentStep = PermissionStep.NOTIFICATION
      }
  }
  ```
  - 마이크 권한 거부 시에는 `showMicSettingsDialog = true`로 설정하여 사용자에게 알림 (라인 85-91)
  - 위치 권한 거부 시에는 어떤 사용자 피드백도 없음

**참고**: 코드 주석에서 "위치는 선택"이라고 명시되어 있으므로 의도된 동작일 수 있으나, 사용자가 위치 기능이 왜 작동하지 않는지 알 수 없는 문제는 여전히 존재합니다.

### [심각도: 하] LocationPermissionViewModel이 정의되어 있으나 사용되지 않음
- **파일**: `presentation/permission/LocationPermissionViewModel.kt:1-81`

- **근거**:

### 1. "다시 묻지 않음" 상태를 올바르게 감지하는가
**판정: 문제 없음** ✓

근거:
- MicrophonePermissionHandler.kt 라인 46-50과 LocationPermissionHandler.kt 라인 49에서 사용된 로직:

## 검증 노트 (검증자: Fable 5, 2026-07-07)

위 보고는 haiku가 작성한 원본이며, 아래는 코드 재확인을 통한 교차 검증 결과다.

### 발견 #1 — 확증, 시나리오를 더 구체적으로 정정

방향은 맞고 [요검증] 표시도 적절하나, 가장 확실한 발생 경로는 haiku가 든
"설정에서 거부 후 복귀"가 아니라 그 **반대**다. 설정에서 권한을 **회수**하면
Android가 앱 프로세스를 종료하므로 다음 실행 시 처음부터 재평가되어 오히려
안전하다. 문제는 **허용** 경로다:

- 시나리오: 마이크 권한 거부 상태로 앱 진입 →
  MicrophonePermissionSettingsDialog 표시(UnifiedPermissionHandler.kt:211-216,
  닫기 버튼 없는 차단형) → 설정에서 마이크 **허용** 후 복귀 → 권한 허용은
  프로세스를 종료시키지 않고, `PermissionChecker.hasMicrophonePermission()`은
  Compose 상태가 아닌 일반 함수 호출이라 권한 변화가 recomposition을 유발하지
  않음 → 다이얼로그가 계속 떠 있고, 사용자는 앱을 강제 종료 후 재실행해야 한다.
  어르신 사용자 기준 사실상 막다른 화면이다.
- 근거: 211행의 게이트는 composition 중 일반 함수를 호출할 뿐 snapshot 상태를
  읽지 않으므로, 다른 이유로 recomposition이 일어나지 않는 한 재평가되지 않는다.
  ON_RESUME 시 권한을 다시 읽어 상태에 반영하는 LifecycleEventObserver가 없다.
- 심각도 "중" 유지 (앱 재시작으로 복구 가능).

### 발견 #2 — 기각 (보고 기준 미달)

"잘못된 동작"이 아니라 UX 개선 제안이다. 코드 주석(104행 "위치는 선택이므로
다음으로 진행")이 보여주듯 조용히 넘어가는 것이 의도된 설계이고, haiku 스스로도
"의도된 동작일 수 있으나"라고 적었다. 수행 규칙의 보고 기준(구체적 오동작
시나리오 필수, 개선 제안 제외)에 따라 발견에서 제외한다.

### 발견 #3 — 기각 (보고 기준 미달)

미사용 코드(dead code)는 실패 시나리오가 없는 정리 대상이지 버그가 아니다.
같은 범주의 관찰로, UnifiedPermissionHandler.kt:68-71의
`showLocationSettingsDialog`/`showNotificationSettingsDialog`/
`showHealthConnectSettingsDialog`는 어디서도 true로 설정되지 않아 243-285행의
다이얼로그 3개가 도달 불가능한 코드다. 둘 다 버그 목록이 아닌 정리 목록에
기록해 둔다.

### 검증자 추가 발견

#### [심각도: 중] 대략적 위치(COARSE)만 허용하면 온보딩은 성공으로 통과하지만 위치 수집은 영구히 불발됨

- 파일: presentation/permission/UnifiedPermissionHandler.kt:98-99,
  data/location/LocationScheduler.kt:265-269
- 증상: Android 12+에서 위치 권한 요청 시 사용자가 "대략적 위치"를 선택하면,
  온보딩 런처는 COARSE만으로도 허용으로 판정하고
  (`ACCESS_FINE_LOCATION == true || ACCESS_COARSE_LOCATION == true`)
  백그라운드 단계로 진행해 플로우가 정상 완료된다. 그러나
  LocationScheduler.checkPrerequisites()는 FINE이 없으면
  `COARSE_LOCATION_ONLY`로 판정해 수집을 시작하지 않으므로, 매일 아침 알람이
  울려도 조건 미충족으로 수집이 영원히 시작되지 않는다. 사용자는 온보딩에서
  위치를 허용했다고 인식하지만 위치 수집 기능이 조용히 죽어 있다.
- 근거: 온보딩의 허용 판정 기준(COARSE 허용)과 수집기의 요구 기준(FINE 필수)이
  불일치한다. 온보딩 중 이 불일치를 사용자에게 알리거나 FINE 재요청으로
  유도하는 경로가 없다. 설정 화면(SettingsViewModel)에는 상태 표시가 있으나
  사용자가 능동적으로 들어가야 알 수 있다.
