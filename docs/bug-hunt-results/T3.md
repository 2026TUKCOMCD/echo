# T3: 네트워크 계층과 토큰 갱신 - 버그 감사 결과

## 발견 목록

### [심각도: 중] Refresh 실패 시 모든 Exception에서 무분별하게 토큰 삭제

- **파일**: `android/app/src/main/java/com/example/graduation_project/data/api/TokenAuthenticator.kt:40-42`
- **증상**: 
  네트워크 에러, 타임아웃, 또는 서버 에러로 인해 refresh 요청이 실패할 때, 유효한 accessToken과 refreshToken이 모두 삭제된다. 이후 모든 API 요청이 401 오류로 실패하고, 사용자는 자신의 의도와 무관하게 로그아웃당한다. 네트워크가 복구되어도 토큰이 없으므로 복구 불가능하다. 
  
  **구체적 시나리오**: 대화 중에 네트워크가 불안정해서 refresh 요청이 타임아웃 → IOException 발생 → tokenStorage.clear() 호출로 유효한 토큰 삭제 → 모든 후속 API 요청이 즉시 실패 → 사용자가 의도하지 않은 로그아웃 상태 발생.

- **근거**: 
  ```kotlin
  // TokenAuthenticator.kt:36-43
  try {
      val tokenResponse = authApi.refresh(RefreshRequest(refreshToken))
      tokenStorage.saveTokens(tokenResponse.accessToken, tokenResponse.refreshToken)
      tokenResponse.accessToken
  } catch (e: Exception) {
      tokenStorage.clear()  // 모든 Exception을 동일하게 처리
      null
  }
  ```
  
  Exception의 원인은 다양한데 모두 동일하게 처리됩니다:
  - **IOException** (네트워크 에러, 타임아웃) → 토큰은 유효함. 네트워크 복구 후 재시도 가능한데 토큰이 삭제됨.
  - **HttpException with 401** (RefreshToken 만료) → 유일하게 clear()가 필요한 경우.
  - **HttpException with 5xx** (서버 에러) → 토큰은 유효함. 서버 복구 후 재시도 가능한데 토큰이 삭제됨.
  
  올바른 처리는 401 응답만 감지하여 clear()를 호출하고, 네트워크 에러나 서버 에러는 null만 반환하여 재인증 시도를 막되 토큰은 보존해야 합니다.

### [심각도: 중] [요검증] TokenStorage의 스레드 안전성 부재

- **파일**: 
  - `android/app/src/main/java/com/example/graduation_project/data/local/TokenStorage.kt` (전체)
  - `android/app/src/main/java/com/example/graduation_project/data/api/AuthInterceptor.kt:9`
  - `android/app/src/main/java/com/example/graduation_project/data/api/TokenAuthenticator.kt:27-38`

- **증상**: 
  AuthInterceptor와 TokenAuthenticator가 서로 다른 OkHttp 스레드에서 동시에 TokenStorage에 접근할 때, 토큰 값이 부분적으로 쓰인 상태에서 읽혀질 수 있다. 특히 refresh 중에 새 요청이 시작되면, 새 요청의 인터셉터가 불완전한 토큰 상태를 읽을 수 있다. 
  
  **구체적 시나리오**: 
  1. Request A가 Thread-1에서 AuthInterceptor를 통과하며 getAccessToken() 호출 시작
  2. Request B가 Thread-2에서 401 응답 받음 → TokenAuthenticator의 authenticate()가 mutex 내에서 saveTokens() 호출 (putString 2회)
  3. Request A의 getAccessToken()이 putString() 중간에 읽혀질 수 있음 → 토큰 앞부분은 구버전, 뒷부분은 신버전 상태의 값을 읽을 가능성
  
  네트워크 성능이 불안정하고 동시 요청이 많을수록 이 현상의 확률이 높아집니다.

- **근거**:
  ```kotlin
  // AuthInterceptor.kt:7-18
  class AuthInterceptor(private val tokenStorage: TokenStorage) : Interceptor {
      override fun intercept(chain: Interceptor.Chain): Response {
          val token = tokenStorage.getAccessToken()  // 라인 9: mutex 보호 없음
          val request = if (token != null) {
              chain.request().newBuilder()
                  .header("Authorization", "Bearer $token")
                  .build()
          } else {
              chain.request()
          }
          return chain.proceed(request)
      }
  }

  // TokenAuthenticator.kt:22-44
  override fun authenticate(route: Route?, response: Response): Request? {
      if (response.request.header("Authorization") == null) return null

      val newAccessToken = runBlocking {
          mutex.withLock {  // 라인 26: Mutex로 보호 시작
              val currentToken = tokenStorage.getAccessToken()
              // ...
              tokenStorage.saveTokens(  // 라인 38: Mutex 내에서만 호출
                  tokenResponse.accessToken, 
                  tokenResponse.refreshToken
              )
              // ...
          }  // Mutex 보호 끝
      }
  }

  // TokenStorage.kt
  fun getAccessToken(): String? = try {
      prefs.getString(KEY_ACCESS_TOKEN, null)  // 동기화 메커니즘 없음
  } catch (e: Exception) { /* ... */ }

  fun saveTokens(accessToken: String, refreshToken: String) {
      try {
          prefs.edit()
              .putString(KEY_ACCESS_TOKEN, accessToken)
              .putString(KEY_REFRESH_TOKEN, refreshToken)
              .apply()  // apply()는 메모리에 바로 쓰고 백그라운드에서 디스크에 씀
      } catch (e: Exception) { /* ... */ }
  }
  ```

  **문제의 핵심**:
  1. TokenAuthenticator의 Mutex는 OkHttp Dispatcher 스레드를 블록시킬 뿐, AuthInterceptor는 다른 스레드에서 실행될 수 있음
  2. AuthInterceptor.intercept()는 Mutex 보호 없이 getAccessToken() 호출
  3. TokenAuthenticator.authenticate()는 Mutex 내에서 saveTokens() 호출
  4. OkHttp는 여러 요청마다 다른 스레드를 할당하므로, 동시에 읽기와 쓰기가 발생 가능
  5. SharedPreferences의 apply()는 메모리에 바로 쓰고 백그라운드에서 디스크에 쓰므로, 쓰기 중간에 읽을 수 있음

  이 경합(race condition)은 확률적으로 발생하므로 재현이 어렵지만, 코드 분석상 존재합니다.

## 체크리스트 판정

### 1. 여러 요청이 동시에 401을 받으면 refresh가 중복 실행되는가 (동기화 여부)

**판정: 문제 없음**

TokenAuthenticator에서 Mutex를 사용하여 refresh를 동기화합니다. 31줄의 `currentToken != requestToken` 체크로 이미 다른 스레드가 갱신한 토큰을 감지하고, 새로운 refresh 대신 갱신된 토큰을 바로 반환합니다. 따라서 중복 refresh는 발생하지 않습니다.

```kotlin
if (currentToken != null && currentToken != requestToken) {
    return@withLock currentToken  // 다른 스레드가 이미 갱신함
}
```

### 2. refresh 실패(refresh 토큰 만료) 시 무한 재시도 루프가 생길 수 있는가, 로그아웃 처리로 이어지는가

**판정: 발견 #1** 

무한 루프는 없습니다. TokenAuthenticator.authenticate()에서 null을 반환하면, OkHttp는 더 이상의 인증을 시도하지 않고 401 응답을 그대로 반환합니다.

하지만 **발견 #1**에서 설명한 대로, 모든 Exception에 대해 clear()를 호출하므로, 네트워크 에러로 인한 의도하지 않은 로그아웃이 발생합니다.

### 3. TokenAuthenticator 안에서 이미 갱신된 토큰으로 재시도하는지, 옛 토큰으로 다시 refresh를 시도하는지

**판정: 문제 없음**

31줄의 체크 로직이 올바릅니다:
```kotlin
if (currentToken != null && currentToken != requestToken) {
    return@withLock currentToken  // 이미 갱신된 새 토큰 사용
}
```

- `currentToken`: 저장소의 현재 토큰
- `requestToken`: 원래 요청에 사용된 토큰

다른 스레드가 이미 갱신했다면 `currentToken != requestToken`이므로 새 토큰으로 재시도합니다.

### 4. TokenStorage 읽기/쓰기의 스레드 안전성 (Interceptor는 OkHttp 스레드에서 돈다)

**판정: 발견 #2**

AuthInterceptor의 getAccessToken()은 mutex 보호 없이 호출되고, TokenAuthenticator의 saveTokens()는 mutex 보호하에서 호출됩니다. OkHttp 스레드 풀에서 동시 접근 시 경쟁 상태가 발생할 수 있습니다.

### 5. ApiResult 변환에서 HTTP 에러 바디/타임아웃/IOException이 각각 올바른 타입으로 분류되는가

**판정: 문제 없음**

safeApiCall 함수에서 예외를 올바르게 분류합니다:
- `IOException` (타임아웃 포함) → `NetworkError` ✓
- `HttpException with 4xx` → `ClientError` ✓
- `HttpException with 5xx` → `ServerError` ✓
- `CancellationException` → rethrow ✓
- 기타 `Exception` → `UnknownError` ✓

### 6. 로그아웃 시 토큰이 모든 저장 위치에서 지워지는가

**판정: 문제 없음**

AuthRepository.logout()에서 항상 tokenStorage.clear()를 호출하며, TokenStorage.clear()는 SharedPreferences의 모든 항목을 삭제합니다. 토큰이 저장되는 유일한 위치(EncryptedSharedPreferences)에서 완전히 제거됩니다.

```kotlin
suspend fun logout(): ApiResult<Unit> {
    // ...
    tokenStorage.clear()  // 항상 호출됨
    return result
}
```

## 검증 노트 (검증자: Fable 5, 2026-07-07)

위 보고는 haiku가 작성한 원본이며, 아래는 코드 재확인을 통한 교차 검증 결과다.

### 발견 #1 — 확증 (CONFIRMED)

TokenAuthenticator.kt:40-42의 `catch (e: Exception)`이 IOException(타임아웃 포함)과
5xx까지 전부 `tokenStorage.clear()`로 처리하는 것을 코드로 확인했다. 일시적
네트워크 불안정만으로 사용자가 로그아웃되는 실제 버그가 맞다. 심각도 "중" 적절.

### 발견 #2 — 기각 (오탐)

전제가 사실과 다르다. SharedPreferences(EncryptedSharedPreferences 포함)는
내부적으로 스레드 안전하다 — 읽기/쓰기가 synchronized된 인메모리 맵을 거치고,
`apply()`의 메모리 커밋은 원자적이므로 "토큰 앞부분은 구버전, 뒷부분은 신버전"
같은 찢어진 읽기(torn read)는 발생할 수 없다. access/refresh 토큰도 하나의
`edit()...apply()`로 함께 커밋되므로 쌍 불일치도 없다.

실제로 가능한 것은 Interceptor가 갱신 직전의 옛 토큰을 읽는 stale read뿐인데,
그 요청은 401을 받고 TokenAuthenticator의 `currentToken != requestToken` 분기
(31행)로 새 토큰 재시도가 이뤄진다. 이는 설계된 복구 경로이므로 사용자 영향이
없다. haiku가 규칙에 따라 [요검증]을 붙인 것은 올바른 판단이었다.

### 검증자 추가 발견

#### [심각도: 하] [요검증] authenticate()에 재시도 횟수 제한이 없어 서버 이상 시 refresh가 무한 반복될 수 있음

- 파일: android/app/src/main/java/com/example/graduation_project/data/api/TokenAuthenticator.kt:22
- 증상: refresh는 성공(200)하지만 발급된 새 access token까지 서버가 계속 401로
  거부하는 상황(서버 키 롤테이션 직후 검증 불일치, 서버 버그 등)이면,
  401 → authenticate → refresh 성공 → 재시도 → 401 → 다시 refresh...가
  refresh 자체가 실패할 때까지 무한 반복된다. 해당 요청이 끝나지 않고
  refresh 트래픽이 계속 발생한다.
- 근거: OkHttp는 Authenticator가 non-null을 반환하는 한 재시도를 계속한다.
  재시도 요청의 토큰은 방금 갱신한 토큰이므로 31행의
  `currentToken != requestToken` 조기 반환에 걸리지 않고 매번 37행의
  refresh를 다시 수행한다. 표준 사례는 `response.priorResponse` 체인으로
  재시도 횟수를 세어 2~3회에서 null을 반환하는 것인데 그 가드가 없다.
  서버가 정상일 때는 발생하지 않으므로 심각도 "하"로 분류한다.
  (체크리스트 #2의 "무한 루프 없음" 판정은 refresh **실패** 경로에 한해 옳고,
  refresh가 **성공**을 반복하는 경로는 놓친 것이다.)
