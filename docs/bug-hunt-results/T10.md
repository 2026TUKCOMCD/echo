# T10. 서버 — 인증/JWT 버그 감사 결과

## 발견 목록

### [심각도: 상] RefreshToken을 AccessToken으로 사용 가능
- **파일**: auth/filter/JwtAuthFilter.java:30-36
- **증상**: 클라이언트가 refreshToken을 Bearer 토큰으로 전송하면 accessToken과 동일하게 인증된다.
  JWT accessToken의 유효 기간이 1시간인 반면, refreshToken은 30일이므로, 공격자가 refreshToken을 탈취하면
  30일 동안 인증된 요청을 실행할 수 있다. 정상적으로는 accessToken의 만료 후 refreshToken으로 새 accessToken을 발급받아야 하는데,
  refreshToken을 직접 사용하면 이 메커니즘을 우회할 수 있다.
- **근거**: 
  ```java
  if (token != null && jwtProvider.validate(token)) {
      Long userId = jwtProvider.getUserId(token);
      ...
  }
  ```
  JwtProvider의 validate()와 getUserId() 메서드는 JWT의 구조 및 서명/만료만 검증하며, 토큰 타입(accessToken vs refreshToken)을 구분하지 않는다.
  generateAccessToken()과 generateRefreshToken()은 동일한 buildToken() 메서드를 사용하며, subject(userId), issuedAt, expiration만 저장하므로
  토큰 페이로드에 타입 정보가 없다. 결과적으로 refreshToken도 Bearer 토큰으로 유효하다고 판단된다.

### [심각도: 중] 타이밍 공격으로 사용자 존재 여부 파악 가능
- **파일**: auth/service/AuthService.java:47-53
- **증상**: login() 엔드포인트 호출 시 존재하지 않는 loginId와 비밀번호 오류의 응답 시간이 다르다.
  존재하지 않는 아이디: DB 쿼리 후 즉시 InvalidCredentialsException 발생 (응답 시간: ~10ms)
  비밀번호 오류: DB 쿼리 후 passwordEncoder.matches() 호출 (BCrypt는 의도적 지연, 응답 시간: ~100-500ms)
  공격자는 응답 시간 측정을 통해 해당 아이디가 시스템에 존재하는지 판단할 수 있다.
- **근거**: 
  ```java
  User user = userRepository.findByLoginId(request.loginId())
          .orElseThrow(() -> new InvalidCredentialsException("아이디 또는 비밀번호가 올바르지 않습니다."));
  
  if (!passwordEncoder.matches(request.password(), user.getPasswordHash())) {
      throw new InvalidCredentialsException("아이디 또는 비밀번호가 올바르지 않습니다.");
  }
  ```
  보안 모범 사례상, 존재하지 않는 사용자에 대해서도 passwordEncoder.matches()를 호출하여 CPU 시간을 소모해야 타이밍 공격을 방어할 수 있다.
  현재 구현은 findByLoginId() 결과에 따라 실행 경로가 나뉘므로, 응답 시간으로 사용자 존재 여부 추론 가능하다.

### [심각도: 중] [요검증] logout 엔드포인트가 인증 없이 접근 가능
- **파일**: common/config/SecurityConfig.java:43-46
- **증상**: logout 엔드포인트가 permitAll로 설정되어 있어, 인증 없이 누구든 호출 가능하다.
  공격자가 다른 사용자의 refreshToken을 알고 있으면, logout을 호출하여 해당 사용자를 강제 로그아웃시킬 수 있다.
  이는 Denial of Service 공격이나 사용자 경험 저하로 이어질 수 있다.
- **근거**: 
  ```java
  .requestMatchers(
          "/api/auth/signup",
          "/api/auth/login",
          "/api/auth/refresh",
          "/api/auth/logout",  // logout이 permitAll에 포함됨
          ...
  ).permitAll()
  ```
  그러나 로그아웃은 자신의 refreshToken만 삭제하므로, 공격자가 미리 token을 탈취했다면 logout 여부와 관계없이 인증은 가능하다.
  따라서 이것은 설계 문제일 수 있으며, 요구사항 확인이 필요하다.

## 체크리스트 판정

### 1. JWT 만료/서명 오류가 401로 구분되어 내려가는가 (500으로 새는 경로가 있는가)
**문제 없음**

- JwtAuthFilter의 doFilterInternal() (31행): `jwtProvider.validate(token)` 호출 시 모든 예외를 catch하고 false 반환
- JwtProvider의 validate() (49-57행): JwtException과 IllegalArgumentException을 catch하므로 필터에서 예외 발생하지 않음
- SecurityConfig의 authenticationEntryPoint (59-71행): 인증되지 않은 요청에 대해 401 응답
- 따라서 JWT 검증 실패는 모두 401로 응답되며, 500 오류로 새는 경로 없음

### 2. refresh 토큰 재사용 감지/무효화가 있는가, 로그아웃 후 기존 토큰이 살아있는가
**문제 없음**

- AuthService의 refresh() (60-72행): 
  - refreshToken 사용 후 deleteByToken() (70행)으로 DB에서 삭제
  - 같은 refreshToken으로 재사용 시도 시 findByToken() (61행)이 empty 반환 → InvalidTokenException 발생
- logout() (75-77행): deleteByToken() 호출로 refreshToken 무효화
- 따라서 재사용이 감지되고, 로그아웃 후 기존 토큰이 무효화됨

### 3. 필터 체인에서 인증 예외가 GlobalExceptionHandler에 도달하는가 (필터는 컨트롤러 밖)
**문제 없음**

- JwtAuthFilter에서 예외가 발생하지 않음 (validate()에서 모든 예외를 catch)
- SecurityConfig의 authenticationEntryPoint (59-71행)가 설정되어 인증 실패 시 401 응답
- 필터에서 처리되지 않은 예외는 없으므로 GlobalExceptionHandler 불필요
- AuthService의 refresh() 등 컨트롤러에서 throw하는 예외는 GlobalExceptionHandler (18-24행)가 처리하여 401 응답

### 4. 비밀번호 해싱이 적절한가, 사용자 열거가 가능한가
**발견 #2: 타이밍 공격으로 사용자 존재 여부 파악 가능**

- 비밀번호 해싱: BCryptPasswordEncoder (SecurityConfig 31행) 사용 — 적절함
- 메시지 동일성: 존재하지 않는 ID와 비밀번호 오류 모두 동일 메시지 사용 — 적절함
- 그러나 응답 시간이 다르므로 타이밍 공격으로 사용자 존재 여부 파악 가능

### 5. SecurityConfig의 경로 허용 규칙이 의도와 맞는가 (인증 없이 접근 가능한 엔드포인트 확인)
**발견 #3: logout 엔드포인트가 permitAll에 포함됨 (요검증)**

- signup, login, refresh, logout, 헬스 체크, Swagger 문서: 모두 permitAll 설정
- logout의 인증 필요 여부는 설계 의도에 따라 다름 (요검증 필요)

## 검증 노트 (검증자: Fable 5, 2026-07-07)

위 보고는 haiku가 작성한 원본이며, 아래는 코드 재확인을 통한 교차 검증 결과다.

**전제 확인**: server/CLAUDE.md에 따르면 서버는 현재 MVP 단계로 실제로는
`CurrentUserArgumentResolver`가 고정 userId=1을 쓰는 것으로 문서화돼 있으나,
실제 코드(CurrentUserArgumentResolver.java:27-33)는 SecurityContext에서 userId를
꺼내는 정식 구현이다 — 즉 JWT 인증이 실제 동작 중이므로 아래 발견들은 유효하다.

### 발견 #1 — 확증, 그리고 심각도 상향 근거 보강

refresh 토큰과 access 토큰이 JwtProvider.buildToken()(67-76행)에서 구조적으로
동일하고(subject/iat/exp만, 타입 클레임 없음), JwtAuthFilter가 서명·만료만
검증하므로 refresh 토큰을 Bearer로 그대로 쓸 수 있다는 것은 코드로 확증된다.

haiku가 놓친 **더 심각한 귀결**: logout/refresh는 DB의 RefreshToken 행을
삭제하지만(AuthService.java:70,76), JwtAuthFilter.validate()는 DB를 조회하지
않고 JWT 서명만 본다. 따라서 **로그아웃하거나 토큰을 회전시킨 뒤에도, 그
refresh 토큰은 만료(30일) 전까지 access 토큰으로서 계속 유효하다.** 즉 서버에는
refresh 토큰을 무효화할 유일한 수단(DB 삭제)이 있는데, 그 무효화가 access 경로에
전혀 반영되지 않는다. "로그아웃해도 탈취된 토큰으로 30일간 API 접근 가능"이므로
심각도 "상"이 타당하다. (체크리스트 #2의 "로그아웃 후 무효화됨" 판정은 refresh
엔드포인트에 한해서만 옳고, access 경로에서는 틀렸다.)

### 발견 #2 — 확증하되 심각도 하향(하), 더 직접적인 인접 발견 추가

login()의 타이밍 차이(미존재 ID는 BCrypt 생략)는 실재하나, 타이밍 공격은 망
지터에 묻히고 다수 표본이 필요해 단독 심각도는 "하"가 적절하다. `[요검증]`을
붙였어야 한다(측정 없이는 실측 확증 불가).

**더 직접적인 열거 경로(haiku 누락)**:

#### [심각도: 하] 회원가입 응답으로 아이디 존재 여부가 직접 노출됨

- 파일: auth/service/AuthService.java:33-35
- 증상: signup()이 기존 아이디에 대해 DuplicateLoginIdException("이미 사용 중인
  아이디입니다.")를 던진다. 공격자는 타이밍 없이 이 응답만으로 특정 loginId의
  가입 여부를 100% 확실하게 확인할 수 있다. login()이 두 경우 모두 동일 메시지를
  쓰며 열거를 막은 것과 상충한다.
- 근거: 아이디 중복 안내는 정상 회원가입 UX상 필요한 면이 있어(사용자에게
  알려줘야 함) 완전한 취약점은 아니지만, login의 방어와 정책이 어긋난다는 점에서
  기록한다. 심각도 "하".

### 발견 #3 — 기각 (정상 설계)

logout을 permitAll로 둔 것은 **올바른 설계**다. access 토큰이 만료된 상태에서도
로그아웃(= refresh 토큰 폐기)이 가능해야 하므로, refresh 토큰 소지를 인증 수단
삼아 permitAll로 여는 것이 표준 패턴이다. haiku도 근거 마지막에서 스스로 "인증은
어차피 가능하므로 무의미"라고 적어 사실상 자기 반박했다. "타인 토큰을 알면
강제 로그아웃"은 그 토큰을 이미 탈취한 상태를 전제하므로 추가 위협이 아니다.
정상 동작으로 기각한다.

### 검증자 추가 발견

#### [심각도: 하] [요검증] 동일 refresh 토큰 동시 요청 시 이중 발급(refresh race)

- 파일: auth/service/AuthService.java:60-72
- 증상: 같은 refresh 토큰으로 refresh 요청이 거의 동시에 2건 오면, 둘 다
  findByToken()에서 행을 찾은 뒤(61행) 각자 deleteByToken()·issueTokens()를
  수행해 서로 다른 두 쌍의 토큰이 발급될 수 있다. 정상적인 단일 세션 모델
  (login에서 deleteByUserId로 세션 1개 유지)과 어긋나 순간적으로 두 유효 세션이
  생긴다.
- 근거: 조회-삭제-발급이 원자적이지 않다. @Transactional만으로는 동일 행에 대한
  select가 상호 배제되지 않는다(비관적 락이나 삭제 후 행 수 확인이 없음). 실무
  영향은 낮아 "하"이며, 실제 재현은 동시성 타이밍에 의존하므로 [요검증].
